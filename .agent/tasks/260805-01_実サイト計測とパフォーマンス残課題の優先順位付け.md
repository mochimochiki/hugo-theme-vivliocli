# Task-260805-01: 実サイト計測とパフォーマンス残課題の優先順位付け

## WHY: Background
章節番号の走査を直して 2052ページで 21.7秒 → 7.6秒になった(ADR-260805-01)。
残る無駄も調査で4件見つかっているが、どれが実サイトで効くかは未確認。
合成ベンチは全ページが同じ長さで、CSVも画像も含まないため傾向が実サイトと異なる可能性が高い。

## WHAT: Goal
実サイト(約1554ページ)で変更前後を計測し、残課題4件に着手順を付ける。
着手すると決めた課題を個別のタスクチケットに起こすところまで。

## HOW: Design
`bench-theme.sh`(このタスクの成果物として同梱)で `c958e55`(変更前)と `main`(変更後)を比較する。
体感が改善していなければ `hugo --templateMetrics --templateMetricsHints` で内訳を取り、
下の候補表のどれが上位に来るかで着手順を決める。

計測時に必ず守ること(今回2度、これを守らず誤った結論を出した):
1. テーマの切り替えは `--themesDir` ではなく `hugo.toml` の `themesdir` を書き換える
   (`--themesDir` は設定ファイルの `themesdir` を上書きしない。`hugo config` は上書きされたと表示するので気づけない)
2. 出力に識別子を埋め、どちらのテーマが実際に使われたか毎回確認する
3. 同じ条件を3回以上走らせる(単発の測定は外れることがある)
4. 変更前後の出力がバイト単位で一致することを確認する

## Decisions
- 実サイトの数字が出るまで、残課題には着手しない。
- メニュー配布方法の見直しは `file:` での閲覧を壊さないことが絶対条件(実績があるため)。
  JavaScript で外部ファイルを読む案は `fetch` が `file://` で CORS ブロックされるため不可。
- `site.Store` は採らない。速度の得が無く(2052ページで実測ほぼ同値)、`hugo server` の
  再ビルドをまたいでリセットされないため章節番号が古いまま残る。

## Relevant files
- `layouts/partials/menu.html` — 全ページにメニューHTMLを埋め込んでいる箇所
- `layouts/partials/content-with-section.html` — 1ページにつき2回実行される
- `layouts/partials/csv/get-csv-merge-mask-v.html` — セルごとに配列全体を作り直す
- `layouts/partials/csv/render-table-bodycell.html` — セルごとに `RenderString`
- `layouts/partials/functions/getRootPDFParam.html` — 16箇所から未キャッシュで呼ばれる

- [ ] `hugo server` の初回起動時間と、原稿保存後の再ビルド時間も測る(プレビューが主訴のため)
- [ ] 改善が不十分なら `--templateMetrics --templateMetricsHints` で内訳を取る
- [ ] 候補表を実測値で埋め、着手順を決める

## Gates
- [ ] 実サイトでの変更前後の数字が、3回以上の実行で記録されている
- [ ] 変更前後の出力が一致している(または差分の理由が説明できている)
- [ ] 残課題4件それぞれに「着手する/しない」と根拠が付いている

## Notes

### 残課題の候補(2026-08-05 時点、合成ベンチでの観測)

| 候補 | 内容 | 効く条件 |
|---|---|---|
| メニューの配布方法 | 全ページに全サイト分のメニューを埋め込む。2000ページで1ページ231KB・出力475MBとなり、本文3KBに対し98%以上がメニュー。超線形の伸びの主因 | 数千ページ規模 |
| `content-with-section` | 1ページにつき2回実行される(`single.html` と PDF目次の `toc.html`)。内部も「見出し数 × 本文長」で本文全体を何度も走査 | 本文が長いページ・PDF |
| CSV描画一式 | セルごとに Markdown をフル解釈、縦マージ判定が「行 × 列^2」、`trim-column-id` がセルごとに2回 | 表が多いページ |
| `getRootPDFParam` | 16箇所から未キャッシュで呼ばれる(画像1枚ごとにも) | 画像・表が多いページ |

`getRootPDFParam` をキャッシュ化する場合、**ページ単位のキーで partialCached してはならない**
(ADR-260805-02 と同じ罠を踏む)。

### 補足: この方針を決めた質疑の要約

| 問 | 選択肢 | 選択 | 理由 |
|---|---|---|---|
| 1. どの作業が遅いか / 規模 | プレビュー / 全ビルド / PDF生成 | プレビューと全ビルド、1000ページ超 | PDF生成は `isPDF=true` でメニューを出さないため元々影響が小さい |
| 2. メニューをどう作り直すか | 外部ファイル化 / 生成回数削減 / 範囲を絞る / 段階的 | 段階的(生成回数削減を先行) | 代償のない改善を先に取り切る |
| 3. 変更範囲 | メニューと章番号のみ / +getRootPDFParam / +content-with-section / 全部 | メニューの共有ファイル化まで | (後に前提が崩れ無効化) |
| 4. 旧方式を設定で残すか | 残さない / 既定を新方式 / 既定を旧方式 | (前提が崩れ無効化) | `file:` 経由の利用実績があり壊せないため、外部ファイル化自体を取り下げ |
| 5. 速度と正しさのどちらを採るか | partialCached / site.Store / 使い分け / 設定で選択 | 常に partialCached | トレードオフは存在しなかった。85秒は正しさの代償ではなく不具合だった |
| 6. PR #103 をどうするか | マージ / 実サイト計測後 / 他もまとめて | マージ | 単独で完結し、劣化する規模が存在しない |
| 7. 次にどこへ進むか | 実サイト計測 / メニュー / その他の無駄 / 打ち止め | 実サイト計測 | 何を直すべきかは合成ベンチでなく実サイトの数字が決める |
| 8. 文書化の形 | ADRのみ / ADR+task / +roadmap / 保留 | ADR + task | ルールは必ず残す。優先順位は計測後に付ける |

質問2〜4は「1000ページで85秒が壁」という前提で議論したが、その85秒は
変更そのものが持ち込んだ不具合(ADR-260805-02)であり、前提ごと無効になった。
